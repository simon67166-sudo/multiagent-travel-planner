## 赛道题目

未来的旅游服务不再只是一个 App 或网站，而可能由多个智能体协同完成，例如：
- 用户 Agent（代表游客的意图、偏好、预算）
- OTA Agent（负责搜索/比价/预订）
- 酒店 Agent（代表酒店方的库存、定价、服务能力）
- 达人 Agent（KOL/向导类，提供攻略、行程灵感、本地化建议）

**任务**：围绕真实旅游场景，设计一个有价值的多智能体（Multi-Agent）旅游服务方案。

## 评分标准

聚焦 AI Agent 在**文旅落地应用**上的实际价值，**拒绝空泛概念方案**，欢迎**硬核创新**。评委关注可落地、可验证的具体场景解决方案，不是纯概念性的架构设想。

- 方案必须锚定具体、真实的旅游场景痛点，不能停留在"多智能体协同"的抽象叙述。
- 优先给出可运行/可演示的原型思路，而非纯 PPT 级方案。
- 强调技术或场景上的差异化创新点，避免与常见 OTA/客服机器人类方案同质化。

## 一、产品形态：三面板 UI

- **左上**：类小红书社区 feed（内容/灵感浏览）
- **左下**：地图模块（实时呈现路线与方案）
- **右侧**：聊天 AI 交互界面（控制面）

三个面板不是孤立功能拼接，而是编排 Agent 的三个联动输出通道——聊天驱动状态变化，社区和地图随之同步更新（例如点进社区某条内容会在地图上高亮对应地点）。

## 二、Agent 划分

| Agent | 职责 | 模型档位 |
|---|---|---|
| **编排 Agent**（代表用户，星型架构唯一中枢） | 拆解意图、维护用户状态（人格 + 行程状态）、调用各子 Agent、做多目标权衡与最终裁决 | 强模型（全系统推理最重） |
| **达人/内容 Agent** | 检索/排序社区内容，两阶段检索（人格相似度 → 内容相关性），提炼结构化信息（地点/时段/人均消费/避坑提示），驱动左上面板 | 强模型（主观审美/风格理解，UGC 语义提炼） |
| **行程/路线 Agent** | 把地点和时间约束转成具体路线，调地图/路径规划能力，驱动左下面板；节奏偏好（人格维度）决定路线密度 | 轻量模型或非 LLM（本质是调算法/API，LLM 只做自然语言包装） |
| **OTA/酒店 Agent** | 查库存、比价、预订与退改规则；酒店 Agent 独立于 OTA Agent（二者利益不完全一致：酒店想卖库存，OTA 想赚差价） | 轻量模型（结构化查库存比价，接近查数据库） |
| **异常应变 Agent** | 监听外部事件（航班延误、天气突变、门票售罄），主动触发编排 Agent 重新规划。是否作为 demo 核心演示环节：**待定** | 中等模型（调用频率低，事件语义理解中等复杂度） |

## 三、协作机制：中心化编排（星型）— 已定

编排 Agent 是唯一中枢，其余 Agent 都是被调用的工具化子 Agent，彼此不直接对话。

**Why 选中心化而非去中心化协商**：
- 中心化：调用次数固定、上下文更小、成本更低更可控。
- 去中心化（子 Agent 间多轮直接协商达成一致）：更能体现"多智能体协同"的差异化，但协商轮次和收敛性难控制，容易导致成本失控或 demo 卡顿。
- 决策：**选择中心化，理由是节约成本、工程可控性更高**。

## 四、用户状态设计：旅行人格系统（核心亮点）

这是本方案最有价值的部分——把"社区推荐"从静态内容检索，变成一个**有反馈闭环的用户画像系统**，用具体数据结构和算法讲清楚，而不是依赖"AI 自己想明白"的模糊叙述。

### 4.1 状态结构

人格不是达人 Agent 私有逻辑，而是编排 Agent 维护的**共享用户状态**，多个子 Agent 都会读取：

```
用户状态 = {
  静态人格: { 节奏偏好（特种兵型/休闲型）, 口味偏好, 经济实力, ...更多维度 },
  动态行程状态: 本次规划中的地点/时间/已确认预订
}
```

- 人格影响达人 Agent（检索排序）、行程 Agent（路线密度）、OTA/酒店 Agent（预算过滤）。
- **人格应场景化，而非焊死标签**：同一用户"出差"和"度假"可能是完全相反的偏好（务实高效 vs 悠闲探索），人格向量应按"本次旅行模式"分场景存储，不能给用户焊死一个静态标签。

### 4.2 相似度优先推荐（两阶段检索）

达人 Agent 检索社区内容时：
1. 先按人格向量相似度筛出"像我的人"发的/沉淀的内容
2. 再在相似人群内部做内容相关性排序

技术上可用向量库实现（ModelScope 上有现成 embedding 模型，免费算力可支撑，能真正跑起来演示，不是纸面概念）。

**量化展示**：在社区面板直接显示"3 位和你人格相似度 92% 的人去过这里，人均花费 XX，评分 4.8"这类具体数字，比"大家都说好"更有说服力，也更容易在 demo 中让评委一眼看出这不是随便推荐的。

**经济实力应作为硬过滤而非加权项**：避免给预算中等的用户种草消费不起的土豪玩法内容，导致"心动但订不起"的体验问题。

### 4.3 执行完的行程自动沉淀为帖子（核心创新点）

社区内容不完全来自用户主动发帖，而是**用户执行完的、真实发生过的旅行计划**会被系统留存，转化为社区帖子。

**价值**：
- 解决传统 UGC 社区（如小红书）内容真实性存疑的问题（软广、滤镜、过度种草）——本方案的帖子有真实行程数据佐证，可打"已验证行程"标记。
- 解决冷启动问题：不需要主动招募达人入驻，用户用得越多内容池自己滚起来，形成正向飞轮。

**实现**：不需要单独的"发帖 Agent"，从结构化行程数据 + 用户反馈生成帖子，可以模板化拼装 + 轻量 LLM 润色，不必走完整 Agent 推理，节省成本。

### 4.4 反馈机制校准人格（闭环）

用户旅行归来后对计划进行点评，反馈校准人格定义，形成闭环：

```
用户人格 → 推荐内容 → 生成行程 → 执行 → 反馈评价 → 校准人格 → 更精确的下一轮推荐
```

**反馈粒度要拆开，不能只打总分**：应针对具体环节反馈（这个景点值得吗/这家店踩雷了吗/这个节奏是不是太赶），让每条反馈精确更新人格向量里对应的维度，而不是笼统调整一个总分导致无法归因。

## 五、待解决的风险点（评委大概率会问）

1. **冷启动**：新用户没有历史行程，人格从哪来？建议轻量 onboarding（几道选择题，如"更喜欢排满行程还是留白"）给出粗糙初始向量，后续用反馈持续校准。
2. **隐私/公开意愿**：行程自动沉淀成帖子，用户不一定愿意公开完整行程和消费数据。需要"是否公开/脱敏"确认环节，不能默认全量公开。
